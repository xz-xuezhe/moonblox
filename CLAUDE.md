# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**MoonBlox** is a Markdown-first programmable site generator. Users write Markdown, embed interactive components written in MoonBit, and `moonblox build` outputs a static site.

- Components are written in MoonBit using [rabbita](https://github.com/moonbit-community/rabbita) (Elm-style MVU).
- All components use a unified `pub fn -> @rabbita.Html` interface; the build system wraps them in Cells automatically.
- User directory is pure content — no MoonBit project files. Build generates a temp project in `_moonblox/`.

## Build Pipeline

```
posts/*.md                       components/*/{moon.pkg, *.mbt, *.css}
     ↓                                        ↓
  embedded string                    scanner → _registry.mbt
     ↓                                        ↓
  parse_markdown() ────────────→ render_document() → Cell tree → mount("app")
                                                                      ↓
                                                              moon build --target js
                                                                      ↓
                                                                   dist/
                                                              index.html + index.js + style.css
```

### Pipeline Additions

- **Structured block pre-processing**: `::name { ... }::` blocks are parsed before markdown, extracting shared models.
- **moonblox.json config reading**: Config is read before scanning, customizing input/output/component paths.
- **Table support**: Markdown tables with alignment are supported in the parser.

## Syntax

### Inline component

```md
@badge(text: "new", tone: "info")
@counter(initial: 0)
```

### Container component (wraps Markdown)

```md
:::callout(type: "note", title: "Tip")
Regular **Markdown** content here.
:::
```

## Component Model

All components use a unified `pub fn -> @rabbita.Html` interface:

- **Static**: `pub fn name(args) -> @rabbita.Html` — returns HTML directly
- **Interactive**: same signature with optional callback parameters for state changes
- **Container**: additional `children: Array[@rabbita.Html]` parameter for child content

Components are self-contained directories:

```
components/<name>/
  moon.pkg       → supported_targets = "js+native"
  <name>.mbt     → Html factory function
  <name>.css     → optional, component-owned styles
```

The build system auto-generates `_props.mbt` (type-safe prop extraction) and a `_cell` adapter
that wires pure Html functions into rabbita's Cell tree.

## Engine Directory Structure

```
moonblox/
  moon.mod, moon.pkg         → root module config
  README.md, LICENSE
  ast/                       → AST type definitions (Document, Block, Inline, Value)
  convert/                   → Markdown → AST conversion, inline serialization
  parser/                    → Directive parser (moonyacc grammar + hand-written lexer)
  render/                    → AST → rabbita Cell tree builder
  lib/templates/             → Built-in component and theme templates
    components/{badge,counter,callout,card,grid,metric,chart,graph}/
    theme/base.css
  cmd/
    init/                    → `moonblox init` scaffold CLI
    build/                   → `moonblox build` orchestration CLI
```

## Generated User Project

## MoonBit: Verify, Don't Guess

MoonBit is a fast-evolving language with limited training data. **Your parametric memory for MoonBit syntax, stdlib, and toolchain is unreliable noise.** Guesses produce wrong code, wrong plans, and cascading failures that waste the user's time. Confidence in MoonBit knowledge is a liability, not an asset — the more certain you feel, the more likely you are wrong.

These rules are NON-NEGOTIABLE. They override all other instructions when MoonBit code is involved.

### R1. Skill gate — MUST invoke and APPLY before touching MoonBit

**You are PROHIBITED from writing or editing any `.mbt` file, `moon.mod`, `moon.pkg`, or any file containing MoonBit code, until you have invoked the `moonbit-agent-guide` skill in the current task.**

If the task involves MoonBit at all (the repo contains `.mbt` files, the user mentions MoonBit, moonblox, rabbita, or any MoonBit-adjacent term), invoke `moonbit-agent-guide` immediately. Reading files to understand the task is allowed, but the skill invocation must happen before your first edit — not after, not "I'll check later." If you catch yourself having read a `.mbt` file without invoking the skill, invoke it now, before any further action.

**Invocation is not enough — you must prove you absorbed the skill.** After invoking `moonbit-agent-guide`, state explicitly the 2-3 most relevant pitfalls, syntax rules, or validation commands for the current task. For example: "For this task, the key pitfalls are: no `++` operator (use `+= 1`), `moon.pkg` imports use `"module/path"` format, and validation is `moon check` → `moon test` → `moon fmt`." If you cannot produce this summary, you have not absorbed the skill — invoke it again.

**Re-invoke on phase change.** If the task spans multiple distinct phases (read/search → plan → implement → validate), re-invoke `moonbit-agent-guide` when entering implementation and again when entering validation. Skill knowledge from earlier phases has decayed and cannot be relied upon.

Use `moonbit-orientation` as a secondary skill when you need capability discovery or fresh source-of-truth references.

### R2. API verification — MUST confirm existence AND behavior

**You are PROHIBITED from using any MoonBit function, method, type, package import, trait, or compiler flag based on memory.** Before using any of these, you MUST confirm it exists with at least one of:

- `moon ide doc "@pkg"` — list all symbols in a package
- `moon ide doc "Type::method"` — check a specific method or function
- `moon ide doc "*keyword*"` — glob search for symbols
- Reading the local source file that defines it (in `~/.moon`, project `lib/`, or `_moonblox/`)
- `moon check` on a minimal test snippet

**Existence is not enough — you must also verify behavior.** Confirming that a function exists does not confirm its parameter order, return type, error behavior, or calling convention. After confirming existence, check at least one of: the function's signature via `moon ide doc`, its docstring, or a usage example in existing code. Do not assume MoonBit APIs behave like their equivalents in Rust, Go, TypeScript, or any other language.

If you catch yourself thinking "I recall X exists" or "in most languages you do Y" or "X probably takes/returns Z" — that is a VIOLATION in progress. Stop, and go to verification.

### R3. Tool failure ≠ API absence — MUST retry with different approach

**You are PROHIBITED from concluding a MoonBit capability, API, or feature does not exist based on a single failed command.** A command error is a tool invocation problem, not a feature-existence verdict. When a command fails:

1. **Classify the failure**:
   - **Syntax/argument error** → run `<command> --help`, fix args, retry.
   - **Network error or timeout** (especially accessing GitHub) → retry immediately with `gh` CLI (`gh api repos/owner/repo`, `gh view owner/repo/file.mbt`), which is installed and authenticated locally. Do NOT treat a GitHub network failure as "resource unavailable."
   - **Missing tool** → report the missing tool and ask.
   - **Empty/unexpected result** → try an alternative verification method (different package path, glob search, source read).

2. **Minimum two-method rule**: You MUST attempt at least two distinct verification methods before stating that something does not exist. A single failed `moon ide doc` or `curl` call proves nothing. **The two methods MUST have different failure modes**: at least one must be local (reading source files in `~/.moon`, project `lib/`, `_moonblox/`, or `moon check`) rather than network-dependent. Two network-dependent methods that both fail (e.g., `moon ide doc` + `gh api`) share the same root cause and count as one failed approach, not two. Two methods with different failure modes that both confirm absence is the minimum threshold for a negative claim.

### R4. Validation loop — MUST check AND test before done

**You are PROHIBITED from reporting a task as complete or successful until `moon check` passes with no errors and, when applicable, `moon test` passes for the affected package.** After editing MoonBit code:

1. Run `moon check`. If it fails, fix the errors and re-check. Do not skip this step, do not delegate it to the user, and do not claim "the implementation should work" before the compiler has accepted it.
2. If the package has test files (`*_test.mbt`, `*_wbtest.mbt`, `*.mbt.md`, or docstring tests), run `moon test [package-dir]`. If tests fail, fix the implementation — do not assume the tests are wrong or outdated. A passing `moon check` proves type correctness; a passing `moon test` proves behavioral correctness. Both are the minimum bar.
3. Before finalizing, run `moon fmt`.

## Coding Guidelines

Behavioral guidelines to reduce common LLM coding mistakes.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. No Hardcoding

**Avoid hardcoding content. If unavoidable, extract it as a standalone file — don't inline it.**

- Templates, CSS, config, sample data — these belong in their own files.
- Before hardcoding anything non-trivial, ask. The answer is almost always "extract it."
- A separate file is easier to review, edit, and maintain than a string buried in code.

### 5. Respect the Agreed Path

**If a previously agreed approach hits a blocker, you are PROHIBITED from silently switching to a different approach — especially a fallback that was already discussed and rejected.**

- "Agreed path" means: an option the user chose in discussion, a specification in a doc, or a design decision in an artifact.
- When blocked: (1) stop implementation, (2) report the exact command/attempt and its error output, (3) confirm you have not violated MoonBit R3 (tool failure ≠ absence) before concluding the approach is infeasible, (4) propose 2-3 alternatives with tradeoffs, (5) wait for the user to choose.
- Reverting to a previously rejected fallback is the single most damaging violation — it was rejected for a reason, and unilaterally resurrecting it wastes all prior discussion.
- If you deviate from the agreed path for any reason, the deviation MUST appear at the very top of your response (before any other text) as "DEVIATION: <what changed and why>" so it survives summarization.

### 6. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, no hardcoded content buried in source, no unilateral path changes when the agreed approach hits a blocker, and clarifying questions come before implementation rather than after mistakes.
